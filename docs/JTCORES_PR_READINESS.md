## 1. What jtcores' actual contribution shape looks like (KNOWN, read live from jotego/jtcores)

jtcores has **no `CONTRIBUTING.md`** and **no PR template** at the repository
root or under `.github/` (`.github/` contains only `FUNDING.yml` and
`workflows/`). Contribution conventions live in `modules/jtframe/doc/`:

- `doc/folders.md` — canonical per-core layout:
  ```
  cores/<name>/hdl/   RTL and include files
  cores/<name>/ver/   one subfolder per test bench (game-name, not core-name)
  cores/<name>/cfg/   macros.def, files.yaml, mem.yaml, mmr.yaml, mame2mra.toml, msg, reg.yaml
  cores/<name>/doc/   documentation
  ```
- `doc/style.md` — signal/module naming conventions (`u_` instance prefix,
  `_n`/`_l` suffixes, LHBL/LVBL, module name == file name, top level ends in
  `game`).
- `doc/simunit.md` — CI unit-test discovery: any folder with a `.simunit`
  file, `test.v`/`test.sv` module named `test`, and `gather.f` gets picked up
  by `.github/workflows/simunit.yaml`.
- `cfg/macros.def` — `[target]`-sectioned macro file consumed by
  `jtframe cfgstr`, **not** a raw Verilog `` `define `` header.
- `cfg/files.yaml` — source manifest consumed by `jtframe files` to emit
  `files.qip` (Quartus) and `game.f`/`jtsim_vhdl.f` (simulation). QIP is a
  *generated output* of this file, not the source of truth.
- `cfg/mem.yaml` — declarative SDRAM controller spec; `jtsimson_game_sdram.v`
  in the vendored tree is JTFRAME's **generated** output of this file. Its own
  header says verbatim: *"jtsimson_game_sdram.v is automatically generated by
  JTFRAME / Do not modify it / Do not add it to git."* This file is currently
  checked into this repo (required for a self-contained MiSTer build outside
  the jtframe toolchain) but must never be part of an upstream PR.
- `cfg/mame2mra.toml` — declarative spec consumed by `jtframe mra <core>`
  against `doc/mame.xml` to **auto-generate** MRA files. jtcores does not
  hand-author `.mra` XML the way this repo's `releases/*.mra` files are
  authored.
- Licensing: `rtl/vendor/jtcores/JTCORES-LICENSE` is GPL-3.0 text; every
  vendored donor `.v`/`.sv` file carries a uniform header block
  ("This file is part of JTCORES... Author: Jose Tejada Gomez. Twitter:
  @topapate"). This project's own files never imitate or alter that header
  (confirmed by direct grep — see section 3).

## 2. jtcores already has partial, unfinished scaffolding for esckids (KNOWN — new finding)

This is the most actionable discovery of this pass. jotego's own upstream
tree already anticipates Escape Kids as a future `simson`-family member, but
has not finished it:

- `cores/simson/cfg/mame2mra.toml` `[parse]` section already contains
  `debug={ machine="esckids" }`, but the `[ROM]`, `[buttons]`, `[Audio]`
  regions/entries below it list only `simpsons` and `vendetta` — no
  `esckids`-specific ROM region/button/header entries exist yet.
- `cores/simson/doc/vendetta.cpp` (a reference copy of the MAME driver kept
  for research under jtcores' own `doc/`) already contains
  `vendetta_state::esckids(machine_config &config)`.
- `cores/simson/README.md` "Supported Systems" list is explicitly
  **The Simpsons / Parodius da! / Vendetta only — Escape Kids is not listed.**

Read together: jotego scaffolded `esckids` as a recognized machine name
inside the MRA-generation debug path and kept the MAME driver excerpt on
hand, but the `simson` family's RTL, `mame2mra.toml` ROM/button table, and
supported-systems list were never finished for it. This repo's `jtsimson_*.v`
edits (see section 3) are, as far as this pass could verify, the first
complete `esckids` RTL closure of that gap — which is exactly the kind of
contribution jtcores' own files signal was expected/wanted.

## 4. License and attribution audit

- Confirmed by direct grep across `rtl/esckids/*` and every touched
  `rtl/vendor/jtcores/cores/simson/hdl/*` file: **no `meathax`/project-specific
  copyright strings or MiSTer-only branding appear inside the vendored jtcores
  tree.** The donor GPL-3.0 headers ("This file is part of JTCORES... Author:
  Jose Tejada Gomez") are intact and unaltered in every file checked.
- New files under `rtl/esckids/` that would move upstream
  (`escape_kids_pcm_prefetch.sv`, `jtk053252_mmr.sv`) currently carry **no
  file header at all**, not even a GPL-3.0-or-later notice. Before upstreaming
  either file it needs a header consistent with jtcores' existing convention
  (JTCORES boilerplate + real author attribution — this needs the human
  submitter's decision on how they want to be credited; do not fabricate an
  attribution here).
- `k053252_mmr.yaml` already self-documents its provenance ("source-contract
  copy of the audited JTCORES Run and Gun K053252 register specification,
  cores/rungun/cfg/mmr.yaml") — good practice, worth preserving verbatim in
  any upstream submission.
- Top-level repo `LICENSE` is **GPL-2.0** (`GNU GENERAL PUBLIC LICENSE
  Version 2`), while `rtl/vendor/jtcores/JTCORES-LICENSE` and jtcores upstream
  are **GPL-3.0-or-later**. **Flag, not resolved here:** confirm this
  repository's own new files (the ones destined to move upstream) are
  intended to be released under GPL-3.0-or-later to match jtcores' license,
  not the repo-root GPL-2.0 — this is an ambiguity a human must resolve before
  any file leaves this repo for jtcores, since GPL-2.0-only code cannot be
  relicensed into a GPL-3.0-or-later project without the copyright holder's
  consent.

## 5. Simulation/verification parity gaps

jtcores' own verification convention (read live from `cores/simson/ver/` and
`modules/jtframe/doc/simunit.md`) is structurally different from what exists
in this repo:

| jtcores convention (upstream) | This repo today |
|---|---|
| `cores/simson/ver/<game-name>/` — one folder per **game** (e.g. `ver/vendetta`, `ver/simpsons`), each with `sim.sh`, `trace.sh`, `trace.mame`, `.gtkw` waveform views, and (per `simunit.md`) optionally a `.simunit`-discovered `test.sv` for CI | `rtl/esckids/verify/` — a bespoke Verilator smoke-test harness (`tb_escape_kids_full_smoke.sv`, `tb_jtsimson_scroll_ext_bridge.sv`) not in jtcores' folder shape, no `sim.sh`/`trace.sh`/`.gtkw`/`.simunit` |
| `jtframe files sim <core> --target mister` generates `game.f`/`jtsim_vhdl.f` from `cfg/files.yaml` for simulation | This repo has no `cfg/files.yaml`; source lists are Quartus `files.qip` plus whatever the custom Verilator harness hardcodes |
| CI auto-discovers `.simunit` folders (`modules/jtframe/ver/...`, `cores/<x>/ver/...`) via `simunit.sh` / `.github/workflows/simunit.yaml` | No `.simunit` files exist anywhere in this repo; nothing here would be picked up by jtcores CI as-is |
| `jtframe mra <core>` derives MRA from `mame2mra.toml` + `doc/mame.xml` (jotego's own MAME reference database) | This repo hand-authors two `.mra` files directly |
| No project-level MAME-vs-Verilator differential harness is visible in what was read of jtcores (their `ver/<game>/trace.mame` + `trace.sh` + `.gtkw` appear to be a lighter-weight scripted trace/waveform comparison, not the MCP-driven MAME/Verilator comparator this repo's session uses) | This repo/session uses a custom MAME MCP + Verilator differential loop (`mister-mame-diff` skill) — heavier and more automated than anything observed in jtcores itself |

**To port for a real PR:** a `cores/simson/ver/esckids/` folder (or
`cores/esckids/ver/` if jotego prefers a dedicated `esckids` core folder
rather than folding into `simson` — this needs to be settled with jotego, see
checklist item 2 below), a `cores/simson/cfg/files.yaml` entry list for the
new/changed files, and (once the project decides its RTL is stable) a
`.simunit`-discoverable regression test exercising at minimum the PCM
prefetch module and the K053252 register map, mirroring `simunit.md`'s
required layout (`test.v`/`test.sv` module named `test`, `gather.f`,
`.simunit`). This repo's own bespoke Verilator harness under
`rtl/esckids/verify/` and the MAME MCP differential workflow are legitimate
to keep as this repo's own pre-upstream verification and do not themselves
need to move — only their *conclusions* (a working, regression-tested esckids
mode) need to carry over into jtcores-native test coverage.

## 6. Standing blocker — DO NOT treat as resolved

**There is an active, unresolved functional bug in this session:** on real
MiSTer hardware the core boots, the ROM loads normally, the display flashes
briefly, then the screen goes permanently black with no audio. Root cause is
not yet found. Concurrent differential-debug work in this session has ruled
out a CPU/bus crash across roughly 15–80M simulated Verilator cycles, but has
**not** reproduced the real hardware symptom, and a formal MAME-vs-Verilator
attract-mode comparator is currently blocked on an unrelated MAME
trace-harness defect (observed at the top of this session: `quartus_fit.exe`
and `verilator-safe.exe` processes were running under another concurrent
session at the time this report was written, consistent with that debug work
being in progress).

**This core is not ready to submit to jtcores while this bug stands.** A
jtcores maintainer reviewing a PR for hardware they don't own would have no
way to independently confirm the core boots correctly, and shipping a
known-broken hardware path upstream (even behind an `esckids` flag) risks
jotego's own release quality bar. Any PR preparation must treat this as a
hard blocker, not a "known issue" footnote.

## 7. Checklist — what a human still needs to do before opening a PR

1. **Resolve the black-screen bug and get real MiSTer hardware confirmation**
   that Escape Kids boots to attract mode with video and audio, not just a
   clean Verilator trace. (Blocking — see §6.)
2. **Coordinate with jotego first**, before writing any PR diff, on:
   - whether `esckids` should be folded into the existing `simson` family (as
     its RTL hooks already assume) or should get a new `cores/esckids/`
     folder that pulls shared donor files the way `cores/aliens/hdl/`
     currently does for `jt052109`/`jt051962`
   - the `escape_kids_pcm_prefetch.sv` design (cache/prefetch strategy) —
     this is enough new logic that jotego will likely want to review the
     approach, not just receive a diff
   - whether `escape_kids_auto_run.sv`'s Auto-Run OSD feature belongs upstream
     at all, and if so, wired through jtcores' own `CORE_OSD` macro convention
     instead of as a standalone module
3. **Rebase the diff against current jtcores `master`**, not this repo's
   frozen vendored snapshot (the vendored copy has no submodule/commit
   pinning info recorded in this repo — confirm the exact upstream commit the
   snapshot was taken from before diffing).
4. **Author `cores/simson/cfg/mame2mra.toml` `esckids` entries** (ROM
   regions/order, buttons, header byte, NVRAM default) to replace this repo's
   hand-authored `.mra` files with jtcores' own generation path, and verify
   `jtframe mra simson` produces MRA output equivalent to this repo's
   hand-authored ones.
5. **Write `cores/simson/cfg/files.yaml` additions** for the new files
   (`escape_kids_pcm_prefetch.sv`, `jtk053252_mmr.sv` or its `.yaml` source,
   any new `hdl/` additions) instead of relying on this repo's `files.qip`.
6. **Port at least one jtcores-native regression** into
   `cores/simson/ver/esckids/` (or the new core folder chosen in step 2)
   following the `.simunit` layout in `modules/jtframe/doc/simunit.md`, so
   jtcores CI (`compile_mister.yaml`, `linter.yaml`, `simunit.yaml`) actually
   exercises the esckids path.
7. **Resolve the GPL-2.0 vs GPL-3.0-or-later licensing question** (§4) and add
   proper JTCORES-style headers with correct attribution to the new files
   before they leave this repo.
8. **Run jtcores' own Verilator linter and unit-sim suite locally** against
   the rebased diff (not just this repo's bespoke harness) to catch any
   convention mismatches (naming per `doc/style.md`, lint warnings jtcores'
   CI would flag) before sending the diff to jotego.
9. Only after 1–8: open a PR (or, given the size and design-review nature of
   this contribution, consider opening a discussion/issue with jotego first
   to agree on approach before a full diff).
